# 方案草案：统一每日商品采集队列与低空转 Worker

> 状态：**仅供讨论（Draft）**；本文档不修改实际调度、数据库或 Worker 代码。  
> 目标：保留 SQLite + better-sqlite3 + Node.js/TypeScript + Playwright/Chromium + Docker Compose 技术栈；无需 Redis/BullMQ。  
> 时区：北京时间 `Asia/Shanghai`，每日 19:00 = UTC 11:00。

## 1. 背景与现状（截至 2026-11-16）

- PR #4 已将“新增商品立即首次排队，随后按下一个北京自然日 19:00 进入常规采集”的排期逻辑合并进 `main`。
- 当前常规任务依据每个商品来源绑定表的 `next_due_at` 逐个生成；`collection_jobs` 存已入队任务，`collection_runs` 和 `product_observations` 保存实际运行与销量历史。
- Worker 常驻运行；每轮调用 `scheduleDue()` / `claimJob()`，空闲后固定休眠 5 秒，并刷新 SQLite 心跳。
- 同一来源的商品抓取是串行的，并在**上一请求完成后**至少等待 `XHS_SOURCE_MIN_GAP_SECONDS`（默认 120 秒）。任务重试、来源限制和执行租约已有实现。
- Chromium 浏览器进程会被复用；当前只有 Worker 正常退出或浏览器异常时才关闭，不会根据长时间空闲主动关闭。

## 2. 目标和非目标

**目标：** 把每日定时的“是否应生成任务”从商品级滚动时间改为**北京日期 + 统一 19:00 的批量调度**；保留可恢复的持久化队列并减少空闲轮询及浏览器常驻内存。

**不做：** 不更换 SQLite、不引入 Redis / BullMQ / RabbitMQ、不提高来源采集频率、不绕过平台限制、不删除历史数据；不改变每日 08:00 的 systemd 自动更新部署计划。

## 3. 建议的统一任务生成规则

1. **首次添加/合法启用：** 若商品有效、来源启用且具备有效许可，立即创建一条类型为 `initial` / `activation` 的任务；由 Worker 尽快领取（仍遵循来源的串行、节流、权限和限制条件）。
2. **每日 19:00：** 到达北京时间当日 19:00 时，查询所有仍处于监控中、来源可用且满足实际许可和频率条件的商品，批量生成该**北京自然日**的常规 `daily` 任务。
3. **同日去重：** 常规任务的幂等键建议为 `source_id:product_id:YYYY-MM-DD:daily`（或等价的来源绑定 ID + 北京日期），并由 SQLite 的唯一约束保证重启或多次触发不重复生成。首次任务与常规任务类型区分；若商品在同一北京日期已经发生首次尝试，应避免再次抓取。
4. **严格来源限制：** 来源若明确要求两次访问至少间隔完整 24 小时、48 小时或更长，优先采用来源许可的最小间隔；统一 19:00 不能覆盖更严格条件。
5. **任务状态：** 保留 `queued / running / retry_wait / succeeded / partial / failed / blocked / cancelled` 等真实状态及执行租约。计划时间 `scheduled_for`、尝试时间 `started_at`、完成时间 `finished_at` 与观察时间 `observed_at` 各自独立。
6. **历史及异常：** 停机后恢复时仅为仍有意义的最近一个遗漏采集日补建一个任务（具体追补窗口在实现前落实），不伪造过去各日销量、不一次性补抓多天；跨午夜仍可完成既有任务；阻断来源绝不自动解禁。

## 4. SQLite 设计建议

- **保留**：`collection_jobs`、`collection_runs`、`product_observations`、`source_request_pacing`、`system_heartbeats` 及对应历史、索引和权限设置。
- **从日常调度中移除对商品级 `next_due_at` 的依赖**，改为由“北京日期 + 当日统一触发点 + 幂等键”生成每日任务。
- **过渡兼容**：不要在首个版本直接 DROP `next_due_at`；先停止读取它来决定常规每日排期，待验证完成后再评估清理，避免影响旧 API、监控页面或旧数据。
- **安全升级**：迁移须幂等，部署/重启时不能删除已完成、运行中、首次入队、重试中的任务，也不能把历史快照覆盖为伪造的定时结果。

## 5. Worker 动态唤醒建议

- **有已就绪任务时**立刻领取；有待重试任务时按 `next_retry_at` 唤醒；处于来源节流期时按 `source_request_pacing.next_allowed_at` 唤醒。
- **每日任务**按下一次北京 19:00 设定唤醒；无其他工作时采用**最长约 30 秒**兜底检查，从而发现 Web 进程新插入的即时任务。具体唤醒应采取“最早事件时间”而非永久固定 30 秒，避免推迟 19:00 的统一入队。
- **心跳独立节流**，例如每 60 秒更新一次，但要检查现有健康告警阈值，避免因为心跳间隔改变而误判 Worker 离线。
- 退出信号应能打断休眠并优雅关闭；异常重启后以 SQLite 队列和任务租约恢复，不依赖进程内存状态。
- **浏览器空闲关闭**：在没有执行中的采集任务、且空闲 5 分钟时主动 `closeBrowser()`。连续有任务时继续复用；下次领取任务时按需重启 Chromium。关闭不能打断执行中的页面，继续保留 `chromiumSandbox: true` 和来源主机白名单。
- **不增加额外队列服务**：SQLite 持久化队列仍作为事实来源。

## 6. 需要在实现前评估的边界

- 若 19:00 同时产生大量任务，生成任务和处理任务必须解耦，批量入队采用事务、唯一键和适当分页，避免超长锁。
- 如果正在处理前一日积压任务或失败重试，不得使同一商品过度采集；按真实来源最小间隔进行准入校验。
- 事件驱动通知可减少 30 秒兜底延迟，但 Web 和 Worker 分属不同容器；**本轮先以数据库 + 动态休眠实现**，不引入新的进程间消息组件。
- 不应把数据库写次数减少直接等同于大幅节省 CPU；需分别测量 Worker 空闲 CPU、SQLite 写入量、Chromium RSS/系统可用内存。
- 原有 `PR #4` 的每日自然日逻辑已经上线到 GitHub，迁移策略不能让老商品突然多抓、漏抓或重复生成任务。

## 7. 验收标准

1. 北京日期 19:00（UTC 11:00）统一生成当天符合条件的任务；任务生成与抓取执行时间可以不同。
2. 同一商品同一来源同一北京日期不重复生成常规任务；首次添加不必等待 19:00。
3. 商品仍按来源默认至少 120 秒的**完成后间隔**串行抓取；来源更严格的限制优先。
4. Worker 空闲不再固定 5 秒轮询；即时首采的发现延迟和 19:00 触发偏差有实测结果。
5. 没有执行中的任务、连续空闲 5 分钟后 Chromium 关闭；下一次任务会正常重启。
6. 重启、长时间停机、失败重试、租约超时、跨午夜、大规模队列、来源被阻断及重复唤醒的测试通过。
7. 现有历史销量、任务记录、监控开关与许可状态完整保留；不制造虚假每日销量点。
8. GitHub CI 的单元测试、TypeScript/Next.js 构建、Playwright 沙箱烟测和 Compose 校验通过；生产 VPS 部署后还需通过真实日志和数据库只读检查确认。

## 8. 推荐实施顺序

**阶段 A（正确性）**：新增北京自然日统一入队、幂等键、旧排期兼容与停机恢复测试。  
**阶段 B（资源优化）**：Worker 动态休眠、独立心跳、Chromium 空闲关闭、资源指标/告警与回归测试。

先分别测试再合并各阶段，避免任务排期正确性和资源优化问题同时出现。本草稿 PR **仅记录方案，不实施任何代码改动，也不自动部署**。
